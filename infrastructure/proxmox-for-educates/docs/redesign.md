# Educates on Proxmox VE: redesign

Status: in progress on branch `feature/proxmox-talos`. Phases 1 (cluster) and 2 (cluster services) are written and validated offline: machine configs pass `talosctl validate`, CSI chart values render with `helm template`, and both examples plan. They have not yet run against a real Proxmox cluster.

## Why a redesign

The first Proxmox attempt (fork branch `proxmox`) had these problems:

- **Too many cluster types.** It supported k3s, RKE2 and Talos in one module, and every resource branched on the flavor. Each flavor is one more install and upgrade procedure to keep working.
- **Shell scripts instead of resources.** Most of the Kubernetes setup ran as `local-exec` scripts with `sleep` loops. Changes did not reach clusters that were already deployed. It needed `kubectl`, `talosctl`, `yq` and root SSH to the hypervisors, and it did not work on Windows.
- **Machine config on a CD-ROM image.** The Talos machine configuration, secrets included, was baked into an ISO on Proxmox storage. Talos only reads it on first boot, so later config changes never reached the nodes. The attached CD-ROM also blocked live migration.
- **Talos upgrades destroyed the VMs.** Bumping the Talos version replaced every VM.
- **Unused ingress setup.** It built a Gateway API setup that Educates does not use, and it never deployed Educates.
- **High entry bar.** It needed several Proxmox hosts with HA, hyper-converged Ceph and a jumbo-frame storage network. Most people who want to try Educates have one Proxmox host.

## Goals

1. **Talos Linux only.** A single node covers small setups (the control plane also runs workloads).
2. **Works on one Proxmox host with local storage.** HA, Ceph and a storage network are optional.
3. **Proxmox API only.** No SSH to the hypervisors.
4. **Day-2 operations are part of the design.** Config changes are re-applied. Kubernetes upgrades are declarative. Talos upgrades never recreate VMs.
5. **Same layout as the EKS and GKE modules:** `infrastructure/` + `platform/` + `root-modules/`, with providers configured in the root module.
6. **Scope: the layer below Educates.** This work delivers the cluster and what Educates 4.x expects from it. Installing Educates (`platform/educates`) belongs to the Educates maintainers.

## Architecture

```
root-modules/educates-on-proxmox          providers, wiring, examples
 ├─ infrastructure/proxmox-for-educates   VMs + Talos + Cilium (phase 1), then LB IP pool + CSI drivers (phase 2)
 └─ platform/educates                     Educates itself (maintained by the Educates team, not part of this work)
```

Same layout as EKS and GKE: one `infrastructure/<provider>-for-educates` module that leaves the cluster ready for Educates, and one `root-modules/educates-on-<provider>` that configures the providers and composes it. The two phases are two groups of files in the same module, not two modules.

### Phase 1: cluster (files `10-` to `30-`)

**Image**
- The Talos Image Factory builds a schematic (extensions and kernel arguments) and serves the `nocloud` disk image.
- `proxmox_download_file` downloads it with `content_type = "import"` as qcow2, using only the API. Proxmox does not decompress `import` downloads, so `raw.zst` is not an option.
- VMs import their disk from it (`import_from`, with `ignore_changes`). A new Talos version only replaces the downloaded file.

**Network bootstrap**
- Proxmox's own cloud-init drive gives each VM its IP, gateway and DNS. Talos reads it on the `nocloud` platform.
- No custom ISO, and nothing secret is stored on Proxmox.

**Machine configuration**
- Generated by `talos_machine_configuration` with a pinned config contract (`talos.config_contract`).
- Uses the multi-document format of Talos 1.14.
- Applied by `talos_machine` over the Talos API: in maintenance mode on first boot, then again on every change.

**Bootstrap and upgrades**
- `talos_cluster` bootstraps etcd and owns Kubernetes upgrades: changing `kubernetes_version` runs `upgrade-k8s`.
- `talos_machine` uses `ignore_kubernetes_upgrade_drift`, so it does not fight those upgrades with parallel re-applies.

**Health**
- `talos_cluster_health` closes the apply: etcd, API server and every node Ready.

**CNI**
- Cilium is rendered with `helm_template` into a Talos inline manifest, so nodes come up with networking.
- No kube-proxy. The API is reached through KubePrism (`localhost:7445`), not a single control-plane IP.
- L2 announcements give LoadBalancer IPs on the node network.

**API VIP**
- A Talos `Layer2VIPConfig` holds the API address shared by the control-plane nodes, so there is no external load balancer.

**Gateway API (optional)**
- Installs the standard-channel CRDs as a Talos external manifest. The URL can point to a mirror.
- Enables Cilium's Gateway API controller.

**Topology labels**
- `topology.kubernetes.io/region` is the Proxmox cluster name and `topology.kubernetes.io/zone` is the Proxmox node. Proxmox CSI needs them.

**Proxmox HA (optional)**
- Each VM is registered as an HA resource.

### Phase 2: cluster services (files `40-` and `50-`)

These resources use the `helm` and `kubectl` providers, which the root module configures from the module's own `kubernetes` output (as EKS does). They depend on the phase-1 health check, so they only run against a healthy cluster. The Cilium chart is rendered by a second Helm configuration without cluster access (`helm.template`).


- **LoadBalancer IPs:** a `CiliumLoadBalancerIPPool` plus a `CiliumL2AnnouncementPolicy`.
- **Storage backends.** Choose one or more and pick one as the default class:
  - **Proxmox CSI** (default): RWO volumes on any Proxmox datastore (LVM, ZFS, Ceph RBD, NFS…), created through the Proxmox API with a dedicated token. It is the simplest option on a single host. Limit: a VM can attach only a limited number of SCSI disks, which caps the number of volumes per node.
  - **Ceph CSI**: RBD (RWO) and CephFS (RWX) against an existing Proxmox Ceph cluster, optionally over the storage network.
  - **NFS CSI**: RWX on an existing NFS export. The Educates docs note that NFS-backed storage is not regularly tested.

  For RWX on Proxmox Ceph, use CephFS directly. Exporting CephFS over NFS adds a hop and gains nothing.
- **Pod Security labels** for the namespaces that need `privileged`: the CSI node plugins.
- **No cert-manager and no ingress controller here.** Educates 4 installs them.

### What the cluster offers to Educates

This is the contract between this layer and Educates 4. The Educates installation itself is out of scope.

| Educates 4 expects | Provided by |
|---|---|
| A conformant Kubernetes version the installer accepts (`>= 1.31`) | Talos, `talos.kubernetes_version` |
| A default `ReadWriteOnce` StorageClass | Proxmox CSI (or Ceph RBD); exactly one default |
| `LoadBalancer` Services on ports 80/443, for the bundled Contour Envoy (`envoyServiceType: LoadBalancer`) or a gateway | Cilium LB IPAM and L2 announcements, `load_balancer.ip_pools` |
| A wildcard DNS record `*.<domain>` pointing to the ingress IP | The user (outside this layer); the IP comes from the pool |
| Pod Security: Talos defaults to `baseline`; Educates labels its own namespaces `privileged` where needed | Talos default, unchanged |
| Optional: Gateway API CRDs and a gateway implementation, for when Educates supports Gateway API | `gateway_api` option (Cilium as bring-your-own gateway) |
| Cluster credentials for whoever installs Educates | Root module outputs: `kubeconfig`, plus the `kubernetes` connection object |

On Proxmox, the natural Educates 4 configuration on top of this cluster is:

- `EducatesClusterConfig` in `Managed` mode, with provider `Generic` and bundled Contour exposed as `LoadBalancer`;
- certificates from `StaticCertificate` (a user's wildcard) or `CustomCA` (labs);
- DNS `Manual`;
- policy `Kyverno` (bundled).

The end-to-end test installs Educates this way to prove the layer works. It does not ship a platform module.

**Gateway API:** Educates 4.0 only creates `Ingress` resources. The Educates maintainers are adding Gateway API support, which is already designed and expected within a few weeks. It will bundle [agentgateway](https://agentgateway.dev), or use a gateway the cluster already provides. On this side:

- The cluster can already run Gateway API: CRDs plus Cilium as a bring-your-own gateway (phase 1 option, off by default).
- The LoadBalancer IP pool (phase 2) serves the gateway Service whichever implementation is used.
- To agree once the Educates design is published: who installs the Gateway API CRDs (Educates or this layer), and which version and channel agentgateway needs. Only one owner should install them.

## Decisions

| Topic | Decision | Reason |
|---|---|---|
| Distribution | Talos only | One upgrade procedure; immutable, API-managed nodes |
| Machine config delivery | Talos API (`talos_machine`), not an ISO | Changes reach running nodes; no secrets on Proxmox storage |
| Talos config contract | Pinned variable, separate from the Talos version | Upgrading Talos must not rewrite every node's config |
| CNI | Cilium as a Talos inline manifest | Nodes are Ready right after bootstrap; no CNI chicken-and-egg |
| Cilium API access | KubePrism `localhost:7445` | No dependency on a single control-plane node |
| Talos OS upgrades | `talosctl upgrade`, one node at a time (documented) | Upgrading every node from one `for_each` in parallel can lose etcd quorum |
| Kubernetes upgrades | `talos_cluster.kubernetes_version` | Runs `upgrade-k8s` with health gating |
| In-cluster services | Terraform providers after the cluster exists (phase 2), not shell scripts | Idempotent; updates work |
| Educates installation | Out of scope (`platform/educates` belongs to the Educates team) | This work is the layer below |
| Ingress for Educates | Not installed here; Educates 4 bundles Contour, and later agentgateway | Avoids two owners of the same component |
| Default storage | Proxmox CSI; Ceph CSI and NFS CSI optional | Works with any Proxmox datastore, including on a single host |
| Single-host example | Kept, as the evaluation/lab topology | It is the common user setup and the cheapest end-to-end test |
| Tooling | Plain `tofu`/`terraform`; no Makefile or PowerShell wrapper | Fewer moving parts, works on every OS |

## Results of the first real deployment

Proxmox VE 9.2, three hosts, SDN VXLAN VNet, 1 control-plane node and 2 workers, Proxmox CSI. Educates `4.0.0-alpha.13` installed with its CLI from a jump host, and a sample workshop deployed over HTTPS with a lab CA.

Verified:

- The minimal token privileges. They are now in [requirements.md](requirements.md#credentials).
- CPU baseline `x86-64-v2-AES` on x86-64-v2 hosts: Talos, Cilium, Proxmox CSI and Educates run. ceph-csi 3.18 and later do not: they need x86-64-v3 (AVX2), so x86-64-v2 sites use 3.17.x. preflight.sh checks it.
- PVC deletion with `reclaimPolicy: Delete` removes the Proxmox disk.
- The Educates operator on Talos with the bundled Kyverno and Contour, with the Envoy `LoadBalancer` Service on a Cilium L2 IP.
- MTU on an SDN VNet with `network.mtu = 1`: the VMs inherit the VNet MTU.
- Control-plane HA. Going from 1 to 3 control-plane nodes (one per Proxmox host) was a plain `apply`: 2 VMs and their Talos configuration, with no change to the existing nodes. etcd ended with 3 voting members.
- Control-plane failover. Rebooting the node that was etcd leader and VIP holder moved the VIP to another node. The API through the VIP and the Educates portal never stopped answering (2-second polling during the whole reboot), and etcd elected a new leader.
- `scripts/e2e-test.sh --workshop` passes on both topologies.
- Adding a worker is a plain `apply`: the VM is created directly in the resource pool and joins the cluster. Before that, the `plan` hung for minutes: the health check ran during the plan and waited for the new node. Fixed by making the check depend on every node's configuration.
- Storage network added to a running 6-node cluster: `apply`, then one reboot per node (Talos reads the nocloud network at boot). etcd kept its node-network peer URLs, thanks to the `advertisedSubnets` pin, and every node reached the Ceph monitors over the new NIC.
- Ceph CSI 3.17.2 against the Proxmox Ceph (x86-64-v2 hosts). It used one client for RBD in a RADOS namespace, and one for CephFS in its subvolume group with a dedicated data pool. `rw` (not `rwx`) on the CephFS metadata pool was enough. Kernel modules loaded live, with no reboot. Volumes in `ceph-rbd`, `cephfs` and `vm-lab` (Proxmox CSI) are created, written to, and deleted with their claim.
- Existing nested resource pool, provided by the Proxmox administrator. The token had `PVEPoolAdmin` on that pool only. Moving the 5 running VMs into it was an in-place change with no reboot, and the next plan showed no changes. Two `bpg/proxmox` issues from the previous design did not show with 0.122: the pool-membership race when several VMs join at once, and a pool read gap that made every plan re-add the VMs.

Fixes the deployment needed, all in the module now:

- The Talos image is downloaded as qcow2: Proxmox does not decompress `import` downloads.
- Workaround for a bug in `terraform-provider-talos` v0.12.0 ([siderolabs/terraform-provider-talos#420](https://github.com/siderolabs/terraform-provider-talos/issues/420)): without `image`, `talos_machine` tries an OS upgrade to an empty image on create. The module sets `image` and ignores later changes. Remove the workaround once a fixed release is out.
- The Talos health check passes before Cilium registers its CRDs. The `kubectl` provider retries (`apply_retry_count`).
- On a jump host, the tools wrote caches to the host user's home. `scripts/guest-env.sh` now keeps everything inside the work directory.

## Open points

Findings for the Educates team are collected in [educates-feedback.md](educates-feedback.md).

- **Re-enable VM tags when Proxmox fixes [bug 7864](https://bugzilla.proxmox.com/show_bug.cgi?id=7864).** Proxmox VE 9.2 ignores pool privileges for tags on VM creation. The fix was sent to pve-devel in November 2026 and touches `libpve-guest-common-perl`, `qemu-server` and `pve-container`. Once a release ships it:
  - tell the sites that use pool-only ACLs, so they update Proxmox;
  - set `proxmox.default_tags` back to `true` in the examples and docs;
  - make the `preflight.sh` tags check depend on the Proxmox version.


- Proxmox HA (`proxmox.ha_enabled`) is not tested on real hardware yet: the first site runs without it.
- Single-host evaluation topology: one Talos VM (control plane that runs workloads) is tested on the first site, with Proxmox CSI. Not tested on a standalone Proxmox host: a `local` image datastore (`image_datastore_shared = false`), Proxmox CSI on LVM-thin (`local-lvm`), and a cluster without an API VIP.
- Proxmox cloud-init drive on local storage with Proxmox HA (live migration).
- When Gateway API is enabled, the Cilium operator must see the Gateway API CRDs at its first start. If it starts without them, it disables the feature without reporting it. Talos applies the external manifest in the same pass as the inline one; the end-to-end test checks the result.
- Who installs the Gateway API CRDs once Educates ships agentgateway: this module or Educates.
- **Ingress IP and DNS**, to discuss with the Educates team:
  - The Envoy Service gets the first free IP of the pool, so it has to be pinned by hand (`lbipam.cilium.io/ips`) when the wildcard record points to a fixed IP. Educates 4 has no setting for Envoy Service annotations yet. A generic annotations map would cover every IPAM (Cilium, MetalLB, kube-vip) and cloud options.
  - With Gateway API, `Gateway.spec.addresses` and `Gateway.spec.infrastructure.annotations` cover the same need.
  - The alternative is to let Educates write the record (bundled external-dns). It only supports Route53 and Cloud DNS so far; on-premises DNS (RFC2136, PowerDNS…) would need more providers.
- **Educates workshop NetworkPolicy on Cilium**, to report to the Educates team:
  - The policy (`ipBlock 0.0.0.0/0 except` the metadata IP) blocks in-cluster egress on Cilium, which applies `ipBlock` only to traffic leaving the cluster. That includes GKE Dataplane V2, which is Cilium.
  - `blockedCidrs: []` cannot switch it off.
  - The module works around it with a Cilium policy (`45-educates-compat.tf`, `educates_workshop_egress_fix`). Remove it once Educates fixes this, for example by adding an in-cluster `namespaceSelector: {}` egress rule, or by honouring an empty list.
- The Educates operator pod triggers a Pod Security `restricted` warning on Talos: it lacks `seccompProfile: RuntimeDefault`. It is only a warning, not blocking. To report to the Educates team.
- The Talos health check reports a healthy cluster before every node is `Ready` with its CNI. Consider an extra readiness gate before the cluster services, beyond the retries.

## Possible later additions (out of the current scope)

- **People access through OIDC** (one client per cluster), keeping the admin kubeconfig as break-glass only.
- **Control-plane metrics.** Controller-manager and scheduler bind addresses for scraping. Exposing etcd metrics needs a node reboot.
- **Monitoring agents.** The node-exporter namespace needs the `privileged` Pod Security level. Talos has read-only paths by design, so generic VM alerts must be adapted.
